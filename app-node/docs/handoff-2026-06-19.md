# Handoff — app-node TanStack Start migration (2026-06-19)

Branch: `jdunning/poc/tanstack-on-i18n`. Everything below is committed (not yet
pushed). Backend (Rails/Salesforce proxy) must be on `:3000` for real data.

## How to run

```bash
cd app-node
npm run dev      # Vite dev server on :3001 (HMR; has known dev-only CSS errors, see below)
npm run build    # → dist/client (static assets) + dist/server/server.js (Web fetch handler)
npm start        # node serve.mjs — serves the BUILT site on :3001 (this is the real target)
npm run typecheck   # app-node-owned files only (bridged Rails tree errors are filtered)
```

`serve.mjs` is a zero-dep Node adapter (we did NOT adopt the Nitro v2 plugin —
Nitro v3 is current and we only need a listener). It serves `dist/client`
statically and falls through to the built `fetch` handler. See the decision
record in `rails-retirement-plan.md`.

**Dev vs built differ meaningfully right now** — diagnose layout/CSS issues on
the BUILT site (`npm start`), since the bridge injects CSS at runtime in dev and
TanStack's dev-styles plugin processes CSS per-module (both distort the cascade).

| Route | Status | Shell (header/footer)? |
|-------|--------|------------------------|
| `/` (homepage) | bridged (`ssr:false`) | yes (Rails page self-wraps in `<Layout>`) |
| `/listings/for-sale` | **bridged** | yes |

Bridged pages get the site chrome because the Rails page module wraps itself in
`app/javascript/layouts/Layout.tsx` via `withAppSetup`. Native pages render only
their content — hence no header/footer (see Issue 1).

## Open issues / next steps (prioritized)

### 1. Native pages have no app shell (header/footer) — HIGH
`/listings/for-rent` and `/listings/$id` render bare content. The shared
`Layout.tsx` (SiteHeader + SiteFooter) is **not SSR-safe**: at render it touches
`window.document["documentMode"]`, `window.location.pathname`
(`getLanguageItems`, feedback banner), and pulls `UserContext`/`ConfigContext`
+ `getAssetPath`. Reusing it directly will crash SSR ("window is not defined").

Options:
- Build an SSR-safe native shell in app-node (SiteHeader/SiteFooter from `@uic`
  are window-guarded; the wiring around them isn't) that takes `pathname` +
  asset paths as props, and render it in `__root.tsx` (or a layout route) so ALL
  native routes get it. This also centralizes the shell instead of per-page.
- Or adapt `Layout.tsx` to accept `pathname`/config as props and guard `window`,
  then share it. Bigger blast radius (shared with Rails).

Recommended: a native `<AppShell>` in `__root.tsx`'s `RootDocument`, rendered
around `<Outlet/>`, skipped for routes that supply their own (bridged ones still
self-wrap). Confirm `ConfigContext`/`UserContext` providers exist app-node-side.

### 2. Native `ListingDetail` is incomplete — HIGH
`src/pages/listings/ListingDetail.tsx` was a skeleton. This session the
**preferences** section was made faithful (real `@uic PreferencesList` mapping,
mirrors `modules/listingDetails/ListingDetailsPreferences.tsx`). Still missing
vs the Rails page:
- **AMI / income table** — the route loader doesn't call `getAmiData` and there's
  no AMI section. (`getAmiData` server fn exists in `lib/listings/server-fns.ts`.)
- **Full unit/availability info** — `UnitsTable` is a simplified `StandardTable`;
  the Rails page shows richer unit summary/grouping.
- Neighborhood, building details, leasing-agent contact, application process
  steps, lottery info, etc. — not yet ported.

Port these the same way preferences were done: find the Rails `modules/...`
component, replicate its data→view mapping into an SSR-safe native component fed
by loader data, watch for `window`-at-module-eval imports (inline small helpers
like `preferenceNameHasVeteran` was inlined to avoid `listingUtil`'s window use).

### 3. Dev-only `@reference` errors (e.g. "Cannot apply unknown utility class
`pb-2`") — MEDIUM (dev only)
On `npm run dev`, the rental directory logs Tailwind errors. Cause: TanStack's
dev-server `collectDevStyles`/`fetchCssFromModule` runs each CSS module through
PostCSS **independently**, so global CSS that uses `@apply` without a
`@reference` to the theme can't resolve utilities standalone. Offenders are the
shared globals pulled in via `base.css`: `uic/global/blocks.css`, `forms.css`,
`tables.css` (they use `@apply pb-2` etc. and have no `@reference`). In the
BUILT bundle they're inlined with the theme so `@apply` resolves — hence
build-only-clean. Fix: add `@reference "../../styles/theme.css";` (or the correct
relative path) to those global CSS files, matching how the vendored component CSS
already does. Verify it doesn't double-emit in the production build.

### 4. Translation bugs on the empty rental directory — MEDIUM
Visible on `/listings/for-rent` empty state (already flagged as a spawned task):
- `listingDirectory.emptyListingsView.title.openLotteries` renders as the raw key
  (missing translation key).
- "Get an email" link renders escaped HTML with an unsubstituted `%{target}`:
  `<a href='%{target}' target='_blank'>Get an email</a>`. The `target` interp
  isn't passed and the markup isn't run through `renderInlineMarkup`/Markdown.
Both live in the `EmptyListingsView` native component path.

### 5. `/listings/for-sale` still bridged — LOW
A native `SaleDirectory` exists (`src/pages/listings/SaleDirectory.tsx`). Convert
the route like for-rent once the shell (Issue 1) lands, so it keeps its chrome.

## Cascade layers (so you don't re-debug)

Tailwind v4 layer order is `theme, base, seeds, components, utilities`. Two fixes
this session, both needed because app-node code-splits CSS:
- `__root.tsx` emits `@layer theme, base, seeds, components, utilities;` as the
  **first inline `<style>` in `<head>`** — `@tailwindcss/postcss` relocates the
  in-bundle order statement, so it must be pinned in the document.
- `postcss.config.js` `wrapLayer` skip now matches only `theme.css` (like the
  Rails webpack build), so `base.css` globals wrap into `components` instead of
  staying unlayered (unlayered was beating every layer → serif titles).
- `PreferencesList.css` now `@import`s `InfoCard.css` (per-component CSS needs its
  dependencies; there's no global bundle anymore). Expect similar missing-CSS
  gaps as more `@uic` components are used natively.

Debug technique: agent-browser `eval` walking `document.styleSheets` to report,
for an element, each matching rule's layer (via `parentRule`) and the
`CSSLayerStatementRule` order.
