# Handoff — app-node TanStack Start migration (2026-06-19)

Branch: `jdunning/poc/tanstack-on-i18n`. Everything below is committed (not yet
pushed). Backend (Rails/Salesforce proxy) must be on `:3000` for real data.

**Perf note (nav responsiveness):** native routes' loaders `await` the
Salesforce-proxy calls before SSR emits any HTML, so a cold load waits the full
Rails→Salesforce round trip ("Waiting for server response"). Two mitigations are
now in: (a) `@uic` links route through the TanStack router (client-side nav, no
full document reload) via `src/components/NavigationProvider.tsx`; (b)
`defaultPreload: "intent"` (router.tsx) preloads a route's loader on hover; and
(c) **streaming/deferred loaders** on `/listings/$id`: the loader awaits only the
core listing and `defer()`s the units+AMI (pricing) and preferences sections,
which `ListingDetail` renders via `<Await fallback={spinner}>`. Shell flushes
early — TTFB 1.6s vs 4.3s total. ⚠️ TanStack streams only for non-bot UAs
(`isbot`); bots/crawlers AND `curl` get the full `onAllReady` render, so test
streaming with a real browser UA. Apply the same pattern to the for-rent
directory next.
**Redis caching now works (fixed 2026-06-19).** Two prerequisites: (1) Redis must
be running (`docker run -d -p 6379:6379 redis`) — it's not by default, and with no
server every call misses → Salesforce. (2) There was a bug: `getServerDeps` made a
fresh per-request client with `lazyConnect` + `enableOfflineQueue:false` and
issued the cache READ before awaiting `connect()`, so every GET threw "Stream
isn't writeable" → swallowed as a miss. The cache only ever WROTE, never served.
Fixed with a connected singleton (`src/lib/cache/redis.ts`, `getRedis()`):
`getServerDeps` awaits `ready` once, reads hit a live socket, and the
per-request connect/quit churn is gone. Measured: cold detail load 4.3s → warm
(cache hit) 1.3s. Remaining ~1.3s is SSR render of the big page + the sequential
AMI fetch — that's what streaming/deferred loaders (next step) address.

## How to run

```bash
cd app-node
npm run dev      # Vite dev server on :3001 (HMR; has known dev-only CSS errors, see below)
npm run build    # → dist/client (static assets) + dist/server/server.js (Web fetch handler)
npm start        # node serve.mjs — serves the BUILT site on :3001 (this is the real target)
npm run typecheck   # app-node-owned files only (bridged Rails tree errors are filtered)
```

`serve.mjs` is a zero-dep Node adapter (we did NOT adopt the Nitro v2 plugin —
Nitro v3 is current and we only need a listener). It serves `dist/client`
statically and falls through to the built `fetch` handler. See the decision
record in `rails-retirement-plan.md`.

**Dev vs built differ meaningfully right now** — diagnose layout/CSS issues on
the BUILT site (`npm start`), since the bridge injects CSS at runtime in dev and
TanStack's dev-styles plugin processes CSS per-module (both distort the cascade).

## Open issues / next steps (prioritized)

### 1. Native pages have no app shell (header/footer) — ✅ DONE (2026-06-19)
Resolved. Built an SSR-safe native `<AppShell>` (`src/components/AppShell.tsx`)
and render it in `__root.tsx`'s `RootComponent` around `<Outlet/>`, gated on the
matched route's `staticData.nativeShell`. The native routes (`listings.for-rent`,
`listings.$id`) opt in with `staticData: { nativeShell: true }`; bridged routes
leave it unset and keep self-wrapping in `Layout.tsx`, so no double chrome.

Implementation notes for whoever extends this:
- AppShell uses the **Bloom `@uic` SiteHeader/SiteFooter directly** (window-safe;
  their only window/document access is inside effects/callbacks). It does NOT use
  the Rails `components/SiteHeader` wrapper (that pulls `UserContext` +
  `useFeatureFlag`). Net effect: renders the ACCOUNTS_LAYOUT-off layout and the
  signed-out menu (auth state is client-only localStorage; rendering it in SSR
  would cause a hydration mismatch). Revisit if account chrome is needed natively.
- **Do not import `app/javascript/util/routeUtil` into SSR-eval'd code.** Its
  module top-level builds `SignInRedirectUrls` by *calling* `localizedPathGetter()`
  whose default arg reads `window.location.pathname` → "window is not defined" at
  SSR module eval (crashes every route, since `__root` imports the shell eagerly).
  AppShell inlines a copy of `getLocalizedPath` from SSR-safe `languageUtil`/
  `urlUtil` pieces instead. Same trap as `listingUtil` (handoff Issue 2).
- Asset lookups (`DAHLIA-logo.svg`, `logo-city.png`) go through the new shared
  `src/lib/assetPaths.ts` (extracted from RailsPage; both use it now).
- `Layout.css` is imported by AppShell for the Dahlia header/footer overrides
  (feedback-link, header border). `.site-wrapper`/`.site-content` come from
  `base.css` (already bundled).
- Localized native routes (`/es/listings/for-rent`, etc.) are still bridged via
  the `$lang` route, so they don't get the native shell yet — out of scope here.

Verified on the BUILT site (`npm start`): header (language nav + logo + menu +
feedback banner), footer (seal, descriptions, nav links localized per pathname),
single `#main-content`, no double-wrap on the bridged homepage.

### 3. Dev-only `@reference` errors ("Cannot apply unknown utility class") — ✅ FIXED (2026-06-19)
Fixed by switching Tailwind from `@tailwindcss/postcss` to the `@tailwindcss/vite`
plugin (`vite.config.ts` `plugins: [tailwindcss(), …]`; `postcss.config.js` now
runs ONLY `wrapLayer`). The Vite plugin resolves `@apply` against the full theme
even when the dev server transforms CSS modules independently, so the per-module
PostCSS resolution failure is gone. `wrapLayer` still runs after the plugin
expands `@import "tailwindcss"`, so the cascade-layer ordering is preserved.

Verified the production CSS is unchanged in any way that affects rendering:
byte-diffed the built CSS before/after — the only deltas are (a) CSS-module hash
renames, (b) Tailwind simplifying `calc(var(--spacing) * 0)`→`0` / `* 1`→base,
(c) property reordering, and (d) **a fix**: 16 `@media (… theme("screens.X"))`
queries that the PostCSS build emitted *literally* (invalid → browser-ignored,
so those account-layout breakpoints were dead in app-node) now resolve to rem
values, matching the Rails build. No rendered-content regressions; for-rent
screenshot is pixel-identical. Rails jest (SiteHeader, routeUtil) still pass.

## Cascade layers (so you don't re-debug)

Tailwind v4 layer order is `theme, base, seeds, components, utilities`. Two fixes
this session, both needed because app-node code-splits CSS:
- `__root.tsx` emits `@layer theme, base, seeds, components, utilities;` as the
  **first inline `<style>` in `<head>`** — `@tailwindcss/postcss` relocates the
  in-bundle order statement, so it must be pinned in the document.
- `postcss.config.js` `wrapLayer` skip now matches only `theme.css` (like the
  Rails webpack build), so `base.css` globals wrap into `components` instead of
  staying unlayered (unlayered was beating every layer → serif titles).
- `PreferencesList.css` now `@import`s `InfoCard.css` (per-component CSS needs its
  dependencies; there's no global bundle anymore). Expect similar missing-CSS
  gaps as more `@uic` components are used natively.

Debug technique: agent-browser `eval` walking `document.styleSheets` to report,
for an element, each matching rule's layer (via `parentRule`) and the
`CSSLayerStatementRule` order.
